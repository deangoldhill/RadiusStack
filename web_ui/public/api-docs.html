API Documentation & Tester

Administrator API routes: endpoints available in the selected context. Click an endpoint to stage it in the tester. Write operations are marked and are never sent until you press Send request.

Paging: Users, MAC Auth, Active Sessions, Accounting, Audit Log, and Auth Logs support ?page=1&page_size=25, with page sizes 25, 50, or 100. Paged responses contain items, total, page, pageSize, and totalPages. The read-only GET /api/reports/depleted-allocations supports ?view=summary for current-cycle user/MAC and per-plan counts, or paginated detail with ?page=1&page_size=25&type=user&plan_id=1 (type may be mac). A zero plan allowance is unlimited; counts use the selected tenant's plan usage baseline. Tenant context: a selected tenant shows tenant-specific routes and requests automatically carry X-Tenant-ID; Global shows platform management and operational routes. Only an allowlisted set of read-only operational summaries is available in Global. Plans, downstream destinations, and depleted-allocation details require a selected tenant in multi-tenant mode; Global is not an all-tenant bypass. With multi-tenancy disabled, both platform and legacy single-environment routes appear. RadSec trust model: The per-tenant client certificate CA signs/verifies NAS client certificates; it does not sign the shared listener. Selected authorized tenants with RadSec enabled and provisioned download GET /api/tenant-radsec/download/server-trust-ca as the shared RadSec server trust CA that NAS clients must trust. /server is only the optional public server leaf, never a trust CA. UniFi RadSec: In UniFi, upload only the shared RadSec server trust CA in the CA field because it issued the listener certificate; upload the generated client full-chain PEM and encrypted key in the separate client fields. Do not combine the shared server trust CA and tenant client CA. RadSec client delivery: POST /api/nas/{id}/radsec/client requires {"format":"p12"} or {"format":"pem"}; downloads are separate, authenticated, one-time tokens valid for 10 minutes. NAS client credentials are generated first: P12 has one explicit Download P12 bundle action; PEM exposes separate Download client certificate (.pem) and Download encrypted private key (.key) actions, each consuming its own token only when clicked. PEM private keys are encrypted; the generated passphrase is shown at issuance and can later be revealed to an authorized NAS reader for a supported certificate through GET /api/nas/{id}/radsec/passphrase. Legacy or unrecoverable credentials require regeneration; never paste a passphrase into the tester or a support ticket. Global-only platform, certificate, HA, backup and Radius server-counter routes remain visible only in Global. Tenant management routes follow their individual scope labels: GET /api/tenants returns all tenants for a Global super administrator but only assigned tenants for a permitted tenant administrator; create, edit, delete and membership writes remain Global super-admin operations. Enabling 2FA for a named tenant requires Admins write permission: a Global super administrator can target a tenant by ID, while a tenant administrator must select an assigned tenant and use that same ID in the path. A super administrator operating in a selected tenant must also use that selected ID. Multi-tenancy bootstrap: GET /api/auth/context; tenant management samples are under the Multi-Tenancy group. Replace all {placeholder} path values before sending.

Selected tenant: plans, depleted users and downstream destinations

Choose a tenant you administer first; the app adds X-Tenant-ID: <selected-tenant-id> and the usual authenticated API key. Do not put a real key or shared secret in documentation. The sample IDs and response values below are illustrative, not live account data. These routes need the corresponding Plans, Reports or NAS permission.

GET /api/plans
Response excerpt: [{"id":7,"name":"Starter","depleted_users":2,"data_limit_mb":1024,"time_limit_seconds":0,"reset_period":"monthly"}]
GET /api/plans/{id}/stats
Response excerpt: {"total_users":5,"depleted_users":2,"active_users":3}
GET /api/reports/depleted-allocations?view=summary
Response: {"summary":{"total":2,"users":1,"mac_devices":1,"plans":[{"plan_id":7,"plan_name":"Starter","users":1,"mac_devices":1,"total":2}]}}

depleted_users counts assigned users and MAC devices with exhausted data or time since the reset baseline. A zero limit is unlimited. Plan details and the report use the same selected tenant; Global cannot use this detail route.

GET /api/downstream-destinations
Response excerpt: [{"id":8,"tenant_id":7,"name":"Example","ipv4":"192.0.2.30","auth_port":1812,"accounting_port":1813,"proxy_traffic":"both"}]
GET /api/downstream-destinations/{id}
Response excerpt: {"id":8,"name":"Example","ipv4":"192.0.2.30","auth_port":1812,"accounting_port":1813,"proxy_traffic":"both"}
POST /api/downstream-destinations
Body: {"name":"Example","ipv4":"<destination-ipv4>","auth_port":1812,"accounting_port":1813,"proxy_traffic":"both","shared_secret":"<new-secret>"}
Success response excerpt (201): {"id":8,"radius_reloaded":true}
PUT /api/downstream-destinations/{id}
Body: {"name":"Example","ipv4":"<destination-ipv4>","auth_port":1812,"accounting_port":1813,"proxy_traffic":"accounting"}
Success response: {"success":true,"radius_reloaded":true}
DELETE /api/downstream-destinations/{id}
Success response: {"success":true,"radius_reloaded":true}

On update, omit shared_secret to retain it; the API never reads it back. Traffic accepts auth, accounting or both. A write may be saved but return 503 with saved: true and radius_reloaded: false if activation fails; inspect Radius before retrying. Delete clears dependent NAS routing. NAS/Profile assignments use downstream_destination_id, downstream_mode and downstream_validate_response in their existing full write payloads.

Global-only: platform and HA administration

Only a Global super administrator with Settings permission can call the HA admin routes. The route catalog does not grant cross-tenant access to plans, downstream destinations or depleted-allocation detail. Example values below are illustrative:

GET /api/ha/status
Response excerpt: {"enabled":true,"role":"secondary","queueLength":0,"pause":null,"reconcile":null}
POST /api/ha/log-reconcile
Body: {"confirm":"RECONCILE_LOG_DATA"}
Accepted response (202): {"success":true,"message":"Online log reconciliation started; monitor HA status"}

Reconciliation is destructive maintenance: it requires an enabled primary, explicit Global context, paused delivery and an empty HA queue. Review the node and backup first; do not send the example merely to test access. Use GET /api/ha/status to monitor.

Internal peer-only synchronization (not interactive tester routes): POST /api/sync/batch applies primary-to-secondary changes; POST /api/sync/logs accepts secondary-originated authentication/accounting rows on the primary; POST /api/sync/certificates transfers shared certificate material to the secondary; POST /api/sync/log-reconcile coordinates a reconciliation step; the legacy POST /api/sync/execute is also peer transport. These require encrypted, timestamped HA peer envelopes, not a browser API key or plain JSON. Example response to a paused reverse delivery: 409 {"error":"HA delivery paused or busy"}. An accounting identity conflict instead fails closed and retains the batch for operator review. Do not send these endpoints from the tester.
